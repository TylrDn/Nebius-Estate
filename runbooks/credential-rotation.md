# Credential rotation runbook

Every credential this architecture uses, how long it lives, and how to rotate it. None of them
is ever committed (CONTRIBUTING "No secrets, keys, kubeconfigs, state or real IDs"; gitleaks in CI).

| Credential | Lives | Issued by | Rotate when |
|---|---|---|---|
| User IAM token (`TF_VAR_iam_token`, local runs) | ~12 h | `nebius iam get-access-token` via `scripts/bootstrap-backend.sh` | every session; it is ephemeral in the live roots (never in plans or state) |
| State access key (`AWS_ACCESS_KEY_ID`/`SECRET`) | 1 day | `scripts/bootstrap-backend.sh` (`nebius iam v2 access-key create --expires-at`) | every session; expired keys are harmless, delete them monthly |
| CI service-account key (`NIP_SA_PRIVATE_KEY` environment secret) | `--expires-at` set at registration; in a job, only until the token is minted (`scripts/ci-token.sh` reads it by path into a throwaway CLI config and deletes both) | key pair generated by an administrator; public half registered with `nebius iam auth-public-key create` (the docs do not allow an account's first key through Terraform) | 90 days, or on any suspicion |
| CI state keys (`NIP_STATE_ACCESS_KEY_ID`/`SECRET` environment secrets: read-only in `<stage>-plan`, read-write in `<stage>`) | `--expires-at` set when minted (90 days at most) | administrator, for the stage's read-only and read-write state service accounts | with the SA key, before expiry ([below](#rotating-the-ci-state-access-keys)) |
| Grafana admin password (`grafana_admin_secret_id` set) | SecretStash secret, key `admin-password`; never in plan or state | operator (`nebius mysterybox secret create`, [credentials](../docs/credentials.md#secretstash)) | new secret version, pin it, apply ([below](#rotating-a-secretstash-secret)) |
| Grafana admin password (fallback, no secret id) | state (sensitive output) | `random_password` in `modules/o11y` | taint the resource and apply (`terraform -chdir=... taint 'module.stack.module.o11y[0].random_password.grafana_admin[0]'`); prefer moving it to SecretStash |
| R8 transfer secret keys (`transfer_secret_id` set) | SecretStash secret, keys `destination-secret-access-key` / `source-secret-access-key`; write-only | operator, from the access keys in [credentials](../docs/credentials.md#object-storage-access-key-for-r8) | with the access key's `--expires-at`; new secret version, pin it, apply ([below](#rotating-a-secretstash-secret)) |
| Portal service-account key (`NEBIUS_SA_PRIVATE_KEY_FILE`, also the `nip-portal-viewer` CLI profile) | `--expires-at` set at registration | administrator ([credentials](../docs/credentials.md#portal-read-only-service-account)) | before expiry: register a new public key, point `NEBIUS_SA_PUBLIC_KEY_ID` and the profile at it, restart the portal, delete the old key. `make env-status LIVE=1` warns 30 days ahead |
| Portal billing export S3 key (`NEBIUS_BILLING_EXPORT_*_ACCESS_KEY*`) | `--expires-at` set when minted | administrator ([credentials](../docs/credentials.md#billing-export-pull)) | before expiry (same warning): mint a new key, update `.env`, restart the portal, delete the old key |
| Observability static key (`PROMETHEUS_TOKEN`) | `--expires-at` set when issued | administrator ([credentials](../docs/credentials.md#observability-static-key)) | before expiry: issue a new key, replace it in `.env`, restart the portal, revoke the old one (`nebius iam static-key revoke`) |
| Token Factory API key (`NEBIUS_API_KEY`) | expiry chosen at creation in Token Factory → API keys; owned by a Token Factory service account, not the portal's | the person who created it | before expiry or on any suspicion: create a new key, `scripts/store-credentials.sh NEBIUS_API_KEY` (verifies it live), then delete the old key in Token Factory |
| SSH public key on nodes (`ssh_public_key`) | until the template changes | operator (locally; the pipeline passes `NIP_SSH_PUBLIC_KEY` to R10 `gpu-vm` only) | a template change rolls every node ([blast radius](../docs/change-management.md#kinds-of-change-and-their-blast-radius)) |
| Soperator login SSH keys (`slurm_login_ssh_root_public_keys`) | per apply | operator via `TF_VAR_...` | re-plan with the new list |
| Backups password (`TF_VAR_backups_password`, Soperator prod) | per apply | operator | with the backup bucket's policy; keep the old one until old backups expire |

## Rotating the CI service-account key

**Sandbox after R13 (federation):** once the federated apply job has run green on `sandbox`, its two CI
accounts (`ci_identities.sandbox`, apply; `ci_plan_identities.sandbox`, plan) need no authorized key:
the jobs swap their GitHub OIDC token at STS ([identity](identity.md#retire-the-authorized-keys)).
`bash scripts/live/A4-r13-federated-apply.sh` dispatches that apply, tears its root down, then lists
both accounts' keys and deletes them only on a typed `RETIRE` (and removes `secrets/ci-sandbox*.pem`).
**Until that run's evidence file exists** (`docs/evidence/<date>-sandbox-ci-federated-apply.md`, with
"0 listed after" for both accounts), treat the sandbox keys as live and rotate them below. After it,
sandbox has **no CI service-account key to rotate** ([`platform/ci-keys.yaml`](../platform/ci-keys.yaml)
lists only its state keys, so nothing changes there); keep rotating the sandbox **CI state keys**
([below](#rotating-the-ci-state-access-keys)), which remain. staging and
prod keep their keys until their own federated runs.

The same steps register the first key after the foundation creates the account (`ci = true`).
Uploading an authorized key needs `admin` (the docs list tenant admin); Terraform may upload one
only when the provider itself authenticates with an authorized key, never an account's first key
([authorized keys](https://docs.nebius.com/iam/service-accounts/authorized-keys#uploading-the-public-key)).

```bash
# 1. new key pair (private half never leaves the admin's machine except into the environment secret)
openssl genrsa -out ci-<stage>.pem 4096 && chmod 600 ci-<stage>.pem
openssl rsa -in ci-<stage>.pem -outform PEM -pubout -out ci-<stage>.pub.pem

# 2. register the public half with an expiry; the printed id is NIP_SA_KEY_ID
#    (sa = foundation output ci_identities.<stage>.service_account_id, or ci_plan_identities for the plan job)
nebius iam auth-public-key create --account-service-account-id "$sa" \
  --data "$(cat ci-<stage>.pub.pem)" --expires-at <ISO 8601, <= 90 days> --format jsonpath='{.metadata.id}'

# 3. update the GitHub Environment secrets NIP_SA_PRIVATE_KEY (ci-<stage>.pem) and NIP_SA_KEY_ID
#    and set the key's expires in platform/ci-keys.yaml (make env-status warns 14 days before it)
# 4. run the pipeline's plan job once; then find the old key and delete it:
nebius iam auth-public-key list-by-account --account-service-account-id "$sa" --format json
nebius iam auth-public-key delete --id <old key id>   # not in the docs; per CLI help (nebius 0.12.285)
```

## Rotating the CI state access keys

The pipeline reaches the state bucket with an S3 access key, a **different one per environment**:

| Environment | State account (foundation output) | Its only grant | Why |
|---|---|---|---|
| `<stage>-plan` | `ci_plan_state_identities.<stage>.service_account_id` | `storage.object-viewer` on the bucket | the plan job (no reviewers) can read state, never rewrite it; it plans with `-lock=false` because it cannot write the lock file ([change management](../docs/change-management.md#the-path)) |
| `<stage>` | `state_identities.<stage>.service_account_id` | `storage.object-editor` on the bucket | the apply job re-plans under the lock and writes state |

Never put the read-write key into `<stage>-plan`. Rotate each before its `--expires-at`, and at once on
any suspicion. Each key's expiry is recorded in [`platform/ci-keys.yaml`](../platform/ci-keys.yaml);
`make env-status` warns 14 days before it with a pointer to this section.

```bash
# 1. as an admin, mint the new keys (the old ones keep working until step 5). The docs list
#    tenant admin for access keys; project admin is not confirmed by the docs.
#    <output> is ci_plan_state_identities for <stage>-plan, state_identities for <stage>; the key is
#    named <identity name>-ci-<UTC yyyymmddhhmmss> (docs/naming.md: state keys carry seconds).
mint() { # <output> <environment> <identity name>
  local sa created new_id key
  sa=$(terraform -chdir=terraform/live/foundation output -json "$1" | jq -r '.["<stage>"].service_account_id')
  created=$(nebius iam v2 access-key create --parent-id <stage project id> \
    --name "$3-ci-$(date -u +%Y%m%d%H%M%S)" --account-service-account-id "$sa" \
    --description "CI access to Terraform state ($2)" --expires-at <RFC 3339, <= 90 days> --format json)
  new_id=$(jq -r .metadata.id <<<"$created")
  key=$(nebius iam v2 access-key get --id "$new_id" --format json)
  # 2. write it into THAT environment only (values never touch a file or the terminal log)
  jq -r .status.aws_access_key_id <<<"$key" | gh secret set NIP_STATE_ACCESS_KEY_ID --env "$2"
  jq -r .status.secret            <<<"$key" | gh secret set NIP_STATE_SECRET_ACCESS_KEY --env "$2"
}
mint ci_plan_state_identities <stage>-plan nip-tfstate-ro-<stage>
mint state_identities <stage> nip-tfstate-<stage>
```

3. Verify: dispatch `.github/workflows/terraform.yml` with `action=plan` for one stack of the stage
   (the `<stage>-plan` environment). `terraform init` and the lock-free plan succeeding against the
   bucket prove the read-only key.
4. The `<stage>` environment's key is used only by an apply job: confirm both secrets show
   today's date in `gh secret list --env <stage>`; the next `action=apply` run proves it.
5. Revoke the old key: `nebius iam v2 access-key list --parent-id <stage project id> --all` to find its
   id (name and creation date), then `nebius iam v2 access-key delete --id <old id>`. Neither `list` nor
   `delete` is in the docs; per CLI help (nebius 0.12.285). `list` returns 10 keys per page by default
   (`--page-size` default 10), so without `--all` an old key can be missing from the output.
6. Record the rotation date and the new expiry in the stage's ticket, and set the key's `expires` in
   [`platform/ci-keys.yaml`](../platform/ci-keys.yaml) in the same change: `make env-status` (and
   `make preflight`) warn 14 days before that date and fail once it has passed.

`scripts/ci-token.sh` refuses to run while `NEBIUS_IAM_TOKEN` is set, so a rotation never
silently falls back to a person's credentials.

## Rotating a SecretStash secret

Applies to the Grafana admin password (`grafana_admin_secret_id`) and the R8 transfer keys
(`transfer_secret_id`). Terraform never sees the value outside an apply: the write-only arguments
are re-sent when `sensitive.version` changes, and the version is derived from the pinned secret
version id ([sensitive values](https://docs.nebius.com/terraform-provider/sensitive-values#how-to-update-write-only-arguments)).

1. Create a new version with every key the secret holds; creating a version needs `editor`
   ([create a version](https://docs.nebius.com/mysterybox/secrets/create-version#how-to-create-a-version)).
   A version created with the CLI does **not** become primary; the old one keeps serving until you
   pin or promote the new one.

   ```bash
   read -rs NEW_VALUE   # e.g. openssl rand -base64 24 for Grafana; the new access key's .status.secret for R8
   nebius mysterybox secret-version create --parent-id <secret ID> --description "rotation $(date +%F)" \
     --payload "$(jq -nc --arg v "$NEW_VALUE" '[{key: "admin-password", string_value: $v}]')"
   unset NEW_VALUE
   # R8: one entry per key, e.g. [{key: "destination-secret-access-key", ...}, {key: "source-secret-access-key", ...}]
   nebius mysterybox secret-version list --parent-id <secret ID>   # note the new mbsecver-... id
   ```

2. Pin it: set `grafana_admin_secret_version_id` (or `transfer_secret_version_id`) to the new
   version id in the stage's tfvars. Optionally make it primary too
   (`nebius mysterybox secret update <secret ID> --primary-version-id <version ID>`,
   [make primary](https://docs.nebius.com/mysterybox/secrets/make-version-primary)).
3. Export the value read from the pinned version
   ([credentials](../docs/credentials.md#secretstash)), then plan and apply: the only change is an
   update of the release (or transfer) because its `sensitive.version` changed.
4. Grafana: its admin password setting applies when Grafana creates its database. If the old
   password still works after the apply, reset it in the pod
   (`kubectl -n o11y exec deploy/<grafana deployment> -- grafana cli admin reset-admin-password <value>`).
   R8: delete the old access key once the transfer has run with the new one.
5. Delete the old version only after the apply succeeded
   ([delete a version](https://docs.nebius.com/mysterybox/secrets/delete#how-to-delete-a-version)).

## Revocation

A leaked token or key: delete the access key / authorized key in the console or with the CLI
(`nebius iam v2 access-key delete --id <id>`: not in the docs; per CLI help (nebius 0.12.285);
`nebius iam auth-public-key delete --id <id>`, likewise per CLI help), rotate as above, then
check Nebius Audit Logs for use after the leak time. These are tenant-wide control-plane events,
separate from the stage policy's `audit_logs` (Managed Kubernetes cluster audit logs). Reading
them needs `admin` or `auditlogs.audit-event-viewer`
([roles](https://docs.nebius.com/iam/authorization/roles#audit-logs)):

```bash
nebius audit v2 audit-event list --parent-id <tenant id> --region <region> \
  --start <ISO 8601 leak time> --end <ISO 8601 now> --filter "service.name='IAM'"
```

Use of an S3 access key shows up only as data-plane events (`--event-type data_plane`), and only
for buckets with Object Storage logging on
([view events](https://docs.nebius.com/audit-logs/events/view#how-to-view-events)).
