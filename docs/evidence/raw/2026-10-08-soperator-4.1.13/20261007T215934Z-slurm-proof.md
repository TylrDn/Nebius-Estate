# Lab 04 run 4: Soperator Slurm cluster up on Nebius (evidence)

Captured 2026-10-07 ~22:00 UTC from the live cluster (recipe `soperator-v4.1.13-2`, Soperator 4.1.13, MK8s 1.35,
uk-south1), read through `kubectl exec -n soperator login-0 -c sshd`.

```
$ kubectl get slurmcluster -n soperator
soperator   Available   CONTROLLERS=True   LOGIN=1   SCONFIGCTRL=True

$ sinfo
PARTITION AVAIL  TIMELIMIT  NODES  STATE NODELIST
main*        up   infinite      1   idle cpu-0
hidden       up   infinite      1   idle cpu-0

$ chroot /mnt/jail srun -N1 -p main bash -c "hostname; nproc; head -2 /etc/os-release"
cpu-0
2
PRETTY_NAME="Ubuntu 24.04.3 LTS"
NAME="Ubuntu"
srun_rc=0

$ scontrol show nodes   (excerpt)
NodeName=cpu-0 Arch=x86_64 CPUTot=8 RealMemory=24576 State=IDLE+CLOUD
```

Notes:
- `srun` from the login container's own root fails (`spank: chroot.so` not found): Soperator users work inside the
  shared jail root (`/mnt/jail`), which is where SSH logins land. Run Slurm commands there.
- The recipe's final wait (`wait_for_soperator_activechecks_hr`, up to 240 min) blocks on the `ensure-healthy-nodes`
  active check, which is **suspended** on this CPU-only cluster and stays Pending; the apply cannot finish on its own.
  The fix is described in `docs/soperator-compatibility.md` (active checks).
